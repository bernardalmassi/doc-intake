# Supabase CLI is a devDependency — run it through npx
npx supabase start                  # local stack: API :54321, Postgres :54322, Studio :54323, Inbucket :54324
npx supabase db reset               # drop local DB, re-apply every migration, then seed
npx supabase migration new <name>   # new timestamped file in supabase/migrations/

npm test                            # both projects: tests/unit plus the tenant isolation + extraction suites against the project in .env.test
npx vitest run -t "cannot upload"   # run tests whose name matches
npm run test:db                     # every rolled-back SQL test in supabase/tests (stale runs, the queue), then the two-session lock-order tests in supabase/tests/sessions, via the CLI against the test project (by ref)
npm run eval                        # replay the recorded provider answers for every fixture in evals/, score, check (free, no secrets)
npm run eval -- --live              # re-record missing or stale fixtures against the real providers (costs money; capped)

CI (`.github/workflows/ci.yml`) runs typecheck, lint, build, `test:unit` and `npm run eval` (offline replay) on every push and pull request, with placeholder `NEXT_PUBLIC_*` values and no secrets; actions are pinned to commit SHAs. The Supabase suites run there only when started by hand with the `SUPABASE_TEST_*` repository secrets and the `SUPABASE_APP_URL` repository variable, serialized and never cancelled. No such secrets are set yet, so so far they have only been run locally. Tests that need no database go in `tests/unit/` and must not import `server-only` modules.

`npm test` hits a real Supabase project with real sign-ups (see README "Tests"): the separate **test** project (`doc-intake-test`, `jqhqvtkhijrrvhfwseaq`), never the app's (`rimxdhisbmhjhjdvultm`). It needs `.env.test`, all migrations applied there, and email confirmation off. `scripts/supabase-test-target.mjs` makes both suites and `test:db` refuse to run if the test URL or key is the app's, and the suites refuse a `SUPABASE_TEST_SECRET_KEY` that isn't an `sb_secret_` key or is the app's. Every migration goes to both projects, the test project first: `npx supabase db push --project-ref jqhqvtkhijrrvhfwseaq` (the CLI stays linked to the app project). Users sign in with the publishable key only; keep it that way, since the point is to exercise RLS as a signed-in user. The one exception is the local worker runner (`tests/helpers/local-worker.ts`), which runs the queue worker in-process with the **test** project's secret key: the Vitest `supabase` project maps `SUPABASE_TEST_SECRET_KEY` and `SUPABASE_TEST_URL` to `SUPABASE_SECRET_KEY` and `NEXT_PUBLIC_SUPABASE_URL` for it, aliases `server-only` to its empty module, and runs one file at a time. No test calls a model: the orchestrator and the worker are tested with fake or replayed providers, and Vitest only loads `SUPABASE_TEST_*` variables and blanks `ANTHROPIC_API_KEY` and `OPENAI_API_KEY`, so provider keys can't reach it even from the shell. ## Stack

- Per AGENTS.md, Next 16 differs from older versions: check `node_modules/next/dist/docs/` before writing Next code (e.g. middleware is now `proxy` — see `01-app/01-getting-started/16-proxy.md`; there's also a `02-guides/multi-tenant.md`).

Use `createClient` from `src/lib/supabase/client.ts` in Client Components and the async one from `src/lib/supabase/server.ts` in Server Components, Server Functions and Route Handlers (a new client per request). `src/proxy.ts` refreshes the session on every request; server clients rely on it because Server Components can't write cookies. Auth checks use `requireUser()` / `getCurrentUser()` from `src/lib/auth.ts` (verified via `getClaims`) and are called in every protected page and Server Action, not in layouts or the proxy.
- Env: `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, read in `src/lib/supabase/env.ts`. Optional `NEXT_PUBLIC_REPO_URL`, read in `src/app/site.ts`: the landing page links to the source only when it is set to an http(s) URL. Server-only: `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `EXTRACTION_PROVIDER` (`anthropic` by default, or `openai`), read only in `src/lib/extraction/providers/select.ts`; `SUPABASE_SECRET_KEY` and `EXTRACTION_WORKER_SECRET` (at least 32 characters), read only in `src/lib/extraction/worker.ts`, set only in Vercel (Production, Sensitive), never in `.env.local`. Copy `.env.example` to `.env.local`. Tests read only `SUPABASE_TEST_*` vars from `.env.test` (template: `.env.test.example`). `.env*` is gitignored except the two example files.
- User-facing errors come from `src/lib/errors.ts`: classifiers (`classifyDatabaseError(err, operation)`, `classifyAuthError`, `classifyStorageError`, `classifyRunError`, `classifyThrown`) return only an `ErrorCode`, and the only text a user sees is `userFacingError(code).message`, so no database, provider or document text reaches the page. Every Server Action returns `FormState` (`src/app/form-state.ts`) whose `error` is an `ErrorCode`, never text; the organization page converts each run's stored `error` to a code in `page.tsx` before any component sees it. A code from a URL goes through `isErrorCode` first. Every `raise` in `supabase/migrations/` must map to a code: `tests/helpers/sql-raises.ts` parses every RAISE form in each function's live definition and fails loudly on one it can't read. `ERRORS.md` is kept in step by a test. A new raise or a reworded phrase means updating both.
- Log only through `src/lib/log.ts` (`log.info(event, fields)`): events are a closed list, fields a typed allowlist of closed sets and bounded shapes (a new `error_code` goes in `LOG_ERROR_CODES`; `model` accepts only ids in `PRICING`, optionally with a date snapshot suffix), and every line is scrubbed by `src/lib/redact.ts`. ESLint enforces it: everywhere in `src/lib` and in the Server Actions (`src/app/auth/actions.ts`, `src/app/app/actions.ts`, `src/app/app/extract-action.ts`, the confirm route, the worker route) no `console` and no `process.stdout`/`stderr`; in the server-side code (`src/lib/extraction/`, `redact.ts`, `errors.ts`) also no `console`, `globalThis` or `window` in any form, `process` only as `process.env`, no importing `fs`, `process`, `console` or other stream-writing modules, and no inline `eslint-disable` comments. The rest of `src/lib` is left looser on purpose so browser helpers can live there. Never log a field value, filename, model answer, URL or error message; log `error_kind`, `http_status` or `db_code` instead. `error_code` takes the catalog's codes, so a Server Action logs the code it returns; `src/app/log-fields.ts` turns a Supabase error into those fields. The worker registers its secret key, the bearer and each claim token with `registerSecret`. Unit tests silence it via `tests/setup/quiet-logs.ts`; capture lines with `setLogSink`.
- The Anthropic (`@anthropic-ai/sdk`) and OpenAI (`openai`) SDKs are used with `maxRetries: 0` and an explicit timeout; the orchestrator decides what to retry. Before touching Anthropic code, load the `claude-api` skill and check the SDK types in `node_modules`, not memory.
- `supabase/config.toml` points seeding at `supabase/seed.sql`, which doesn't exist yet. There is no Docker on the dev machine, so `npx supabase start` / `db reset` aren't usable here; validate migration SQL against the test project inside a `begin; … rollback;` block via `npx supabase db query --linked --project-ref jqhqvtkhijrrvhfwseaq -f file.sql` before `db push`. `db push` is gated: show the SQL and `--dry-run` output first. `db push` runs each file as one implicit transaction, not an explicit block, so a top-level `LOCK TABLE` is refused (take it inside a `DO` block) and the rolled-back validation can't catch that.

## Multi-tenant data model

The core design lives in `supabase/migrations/20260917000001_tenants_and_memberships.sql`, and every future table is expected to follow it:

- `tenants` + `memberships` (user ↔ tenant with `tenant_role` enum: `owner` / `admin` / `member`).
- **Every new table carries `tenant_id`** and enables RLS with policies built on the helper functions `private.is_tenant_member(tenant_id)` and `private.is_tenant_admin(tenant_id)` (admin = owner or admin). They were created in `public` and moved to `private` by `20260917000003`, so older migrations still say `public.`. New code must use `private.`
- **Deploying schema changes** (SECURITY.md): migrations go to the test project, then the app project, before the app code that needs them; a signature change ships additively (keep the old form as a wrapper, drop it in a later migration once the deployed app uses the new one). `open_extraction_run(uuid)` was such a wrapper from `20260918000003` until `20260919000002` dropped it. A new parameter gets no default when an overload of the same name exists, or PostgREST refuses the call as ambiguous.
- **Security definer functions go in `private`**, a schema the API doesn't expose, with `execute` revoked from `public, anon`. The only exception is a function meant to be called as an RPC, such as `create_tenant`, or `claim_extraction_run` / `finish_extraction_run`, which are in `public` but executable by `service_role` alone. Otherwise the security advisor flags it (lints 0028/0029).
- **The one table without member policies** is `private.extraction_spend`, the spend ledger: RLS on, no policies, every privilege revoked (`service_role` too), no foreign keys, append-only by trigger for every role. Only definer functions write it.
- **Extensions** (`20260925000002`): `pgmq` (queue `extraction`; its schema, functions and tables revoked from the API roles), `pg_net` (in `extensions`; its grants belong to `supabase_admin` and `postgres` can't revoke them, so they stay as installed; `net` isn't exposed), `pg_cron` (in `pg_catalog`; jobs run as `postgres`). Keep Queues → "Expose Queues via PostgREST" off. Only the app project may hold the Vault pair `extraction_worker_url` / `extraction_worker_secret`; `test:db` fails if the test project has one. No migration may contain a URL but the pricing sources (a unit test checks).
- Those helpers are `security definer` with `set search_path = ''` on purpose: a membership check inside a policy would otherwise re-enter RLS on `memberships` and recurse. Keep new security-definer functions the same way and fully schema-qualify names inside them.
- Tenants are created only via the `public.create_tenant(name, slug)` RPC, which atomically inserts the tenant and the caller's `owner` membership. There is deliberately no INSERT policy/grant on `tenants`. They're deleted only via the owner-only `public.delete_tenant(id)` RPC, which refuses while files remain under the tenant's storage prefix (SQL can't delete storage objects). `public.delete_own_account()` refuses while the caller still owns a tenant.
- Membership role rules (`20260917000004`): nobody changes their own role; only owners grant, change or remove the `owner` role; only `role` is updatable. `private.is_tenant_owner` backs this. A trigger (`memberships_keep_an_owner`, `20260917000007`) refuses any update or delete that would leave a tenant with no owner, for every role, including dashboard user deletion.
- Table auto-exposure is off, and `20260917000006` removed the leftover `truncate`/`references`/`trigger`/`maintain` defaults, so a new table is invisible to the API until you add explicit `grant ... to authenticated` statements (and `revoke execute ... from public, anon` / `grant execute ... to authenticated` for new RPCs), mirroring the end of that migration.
- Slugs must match `^[a-z0-9-]{3,48}$`.

## Documents and uploads (`20260917000008`, `20260917000009`)

Uploads are **row first**. Never send file bytes through a Server Action (1 MB body limit) and never let the client choose a path.

1. A Server Action inserts the `documents` row with **only `tenant_id` and `filename`**. The insert grant covers nothing else: `id`, `uploaded_by` (`auth.uid()`), `status` (`'uploading'`) and timestamps are defaults, and `storage_path` is a **generated column**, always `<tenant_id>/<id>`. Inserting `storage_path` fails with `428C9`; any other extra column fails with `42501`.
2. The browser uploads straight to the `documents` bucket at `storage_path` with the user's session, `upsert: false`, `cacheControl: "0"`. The storage insert policy (`private.can_upload_document_file`) allows it only if a row at that exact path exists, was uploaded by the caller, is still `'uploading'`, and the caller is still a member. There is **no storage update policy**: no overwrite, no move, no upsert.
3. The client calls `public.complete_document_upload(id)`. It requires the caller to be the row's uploader and still a member, the row to be `'uploading'` and the object to exist, then copies `size` and `mimetype` from the storage object's metadata and sets `'pending'`. `size_bytes`, `mime_type` and `status` are never client-writable.

- **Update grant is `filename` only**, and the update policy allows the uploader or a tenant admin, both still members. `filename` is checked to 1–255 characters, not blank, no control characters.
- **Delete is admin only** for both the object and the row, file first: a `before delete` trigger refuses a row while its object exists (`55000`). Because no file can exist without a row, every file is reachable through a row an admin can delete, so `delete_tenant` is never blocked by an orphan.
- **Documents belong to the tenant.** `uploaded_by` is nullable with `on delete set null`; deleting the uploader's account leaves the row.
- **Bucket:** 10 MB, `application/pdf`, `image/png`, `image/jpeg`. This checks the declared `Content-Type` only; the extraction unit must verify magic bytes before anything reaches a model.
- **Download** is a signed URL created on click with a 60 second expiry, never rendered into the page. Don't assert deletion through the authenticated download endpoint: Supabase's CDN serves a deleted object to the same session for a while, and an already-fetched signed URL for the rest of its lifetime. Use the object index (list, minting a signed URL) instead.
- A row in `'uploading'` whose upload never finishes just stays there. Nothing sweeps them yet.

## LLM extraction (`20260918000001` to `20260925000003`)

An admin clicks Extract; the run goes through a queue ([docs/worker-design.md](docs/worker-design.md)). **Spend is checked in the database before the call and cost is computed in the database after it.** Nothing about cost trusts the app, because the Extract action runs as the user and any admin can call `enqueue_extraction_run` over PostgREST.

1. **The Extract action** (`src/app/app/extract-action.ts`) downloads the file with the user's session, counts its pages (`src/lib/extraction/pages.ts`), refuses over 100 pages or uncountable (`checkPageCount`), calls `public.enqueue_extraction_run(document_id, page_count)` and returns `{}`. No token, no model call; the page polls (`RefreshWhileExtracting`, `shouldPoll`). A file that fails to download or doesn't match its type there is still enqueued with no count, and the worker fails it.
2. **`enqueue_extraction_run`**: admin only; document must have a file and not be `processing`; ends a run of this document still in flight after `stale_run_minutes` (10, measured from `claimed_at` when there is one) through `private.reap_extraction_run`; then `private.check_extraction_limits` under a project-wide advisory lock: the tenant's ledger this UTC month plus every run in flight at its estimate (`private.abandoned_estimate`) against 1 USD, the same across all tenants against 3 USD (`53400`), 5 runs per tenant per hour (`54000`); **nothing is inserted before the checks pass**. Then the run as `queued`, the document `processing`, a pgmq message, and `private.wake_extraction_worker()` (pg_net POSTs to the Vault URL with the Vault bearer, after commit). Returns the run id only.
3. **The worker route** (`src/app/api/extraction-worker/route.ts`, `maxDuration = 240`, excluded from the proxy): `401` on a wrong bearer (`worker-auth.ts`), else `202` and `after(() => processOneDelivery({ providers: selectProviders }))`. **The worker** (`src/lib/extraction/worker.ts`, server-only, secret key) calls `claim_extraction_run()` (one message, visibility `worker_visibility_seconds` 300; a second delivery is abandoned at the estimate, never run), then `delivery.ts`: download, magic bytes, a page recount that must equal the enqueued count and be ≤ 100 (else failed at 0 USD, no call), `runExtraction`, then `finish_extraction_run(…, p_cost_estimated, …)`: claim token required, cost from `private.extraction_charge` (clamped to 800 000 / 8 192 at the price in `extraction_model_prices`, longest prefix; unpriced refused), fields and document status as before, one ledger row, message archived, all in one transaction. A refused finish is repeated as `failedCloseAttempts` plans (usage, then the dearest price, `p_cost_estimated` true); only finishes, never model calls. Only `worker.ts` may name `SUPABASE_SECRET_KEY`, `EXTRACTION_WORKER_SECRET`, `"claim_extraction_run"` and `"finish_extraction_run"`, and only the route and `tests/helpers/local-worker.ts` may import it (`tests/unit/worker-boundary.test.ts`).
4. **The sweep** (`private.sweep_extraction_queue`, pg_cron every minute): (a) claimed past its visibility timeout → abandoned at the estimate; (c) `running` with no live message past 10 minutes → abandoned; (d) `queued` past 10 minutes → expired at 0; (b) a message unread for 60 s → woken again, at most 5 a tick. Every in-flight run therefore ends within about 11 minutes. `delete_tenant` refuses while a run is in flight.
5. **The ledger** `private.extraction_spend`: one row per ended run (`charge`, `estimate`, `abandoned`, `expired`, `backfill`), which the ceilings sum by `created_at`. `run.cost_usd` is the display copy.
6. **The lock order** (`20260925000003`, docs/worker-design.md section 15): the tenant row (key share; `delete_tenant` for update), the document, the run, the queue message, the limits' advisory lock. `private.lock_extraction_run(run_id, nowait)` locks a run's document and then the run. A function that must lock out of order never waits: the claim (`pgmq.read` locks the message first) and the sweep (it holds earlier candidates' locks) take the document and the run with NOWAIT in a subtransaction, and the claim rolls its read back on a miss. Any new function that locks more than one of these follows the order. The two-session tests in `supabase/tests/sessions/` race a finish against the sweep and a claim: they commit a fixture (fixed ids, removed by `cleanup.sql`), pg_cron's `extraction-sweep` job is paused around them and turned back on in a `finally` (the run fails unless it is active again with no tick in between; `sweep-pause.sql` refuses if it is already paused), and `scripts/test-db.mjs` starts the second `db query` only once the first has sent its query, because concurrent CLI calls fight over its temporary login role (28P01).

- **The pre-queue RPCs stay until migration 3.** `open_extraction_run(uuid, integer)` and `close_extraction_run(…)` keep their grants, now metered by the ledger and the in-flight rule, so the deployed app keeps working. Migration 3 (`20260926000001_drop_user_run_rpcs.sql`) drops both; it isn't written yet, because any later `db push` would apply it. Its conditions are in docs/worker-design.md, section 8. Nothing in `src/` may call them any more.
- **Config lives in two places on purpose.** `src/lib/extraction/config.ts` holds the thresholds (high ≥ 0.85, medium ≥ 0.6), models, output cap (2048 per call), timeout (60 s per call), retry count, and **mirrors** of the limits (including `workerVisibilitySeconds`) and prices tables. The database is authoritative; `tests/extraction.test.ts` fails if either mirror drifts from the live tables, and `tests/unit/model-prices.test.ts` (no database, runs in CI) reads the price rows out of the migrations and fails if the price mirror drifts from them or if any model in `DEFAULT_MODELS` has no price there. It reads only plain inserts into `extraction_model_prices` and fails on any other statement that writes that table until it is taught the form; `tests/unit/queue-migration.test.ts` does the same for the visibility timeout. Changing a limit or price means a migration that updates the table **and** the mirror, with the date checked. The time bounds must stay 180 s model time < 240 s route `maxDuration` < 300 s visibility timeout ≤ 600 s stale limit (`tests/unit/max-duration.test.ts`).
- **Runs and fields are readable by tenant members and have no write grant or policy at all.** New tables follow the `private.is_tenant_member` pattern; `extraction_limits` and `extraction_model_prices` are readable by any signed-in user and writable by nobody.
- **The JSON schema must contain no unions.** Anthropic's structured outputs reject more than 16 union-typed parameters (found live). "Absent" is an empty string; `validateExtraction` turns it into null. Both providers get the same schema from `buildJsonSchema()`; OpenAI's strict mode also needs `additionalProperties: false` and every property in `required`.
- **Default models:** `claude-sonnet-5` and `gpt-5-nano`. `EXTRACTION_ANTHROPIC_MODEL` selects any priced Anthropic model (`claude-haiku-4-5-20251001` to go back to Haiku). Claude thinking is sent as `disabled` (`ANTHROPIC_THINKING`), because Sonnet 5 otherwise thinks at effort high and spends the 2 048-token output cap. The switch from Haiku isn't justified by the eval alone (EVALS.md). Changing `DEFAULT_MODELS.anthropic` also means updating `abandoned_run_price_model` in a migration. Documents are limited to `maxPagesPerDocument` (100) pages, refused at upload (browser, `src/lib/page-count-browser.ts`), again by the Extract action before enqueuing (`checkPageCount`), and again by the worker's preflight, as are PDFs whose pages can't be counted; the limit keeps the abandoned-run estimate a true upper bound (SECURITY.md, "Stale runs"). Don't raise it without raising the estimate. Model ids and prices come from the providers' pricing pages, dated in the table; don't change them from memory.
- Fields: `document_type` (enum), `title`, `sender_name`, `recipient_name`, `document_date`, `due_date` (YYYY-MM-DD), `payment_terms_days` (whole days, 0 to 3650), `reference_number`, `total_amount` (plain decimal), `currency` (ISO 4217), `summary`. Each carries `confidence`, `band`, `source_text` and, for medium, one `clarifying_question`. Low-confidence values are stored too, for the reviewer. Numeric dates are ambiguous (02/09/2026): the prompt says to decide day or month first from evidence and quote it in `source_text`, and `gateFields` drops both dates to low with a fixed question when the terms and both dates are present and due − document date ≠ the terms (EVALS.md, "Numeric dates"; `tests/unit/dates.test.ts`).
- **The document and its filename are attacker-controlled** (SECURITY.md, "Untrusted document content"). Nothing about the file may reach a prompt: `ExtractionRequest` has no filename (the worker passes none to `runExtraction`), and OpenAI's `input_file` gets the fixed `ATTACHMENT_FILENAME`. The validator's error becomes the retry's user turn, so it may never quote model output. Every answer goes through the output guard (`src/lib/extraction/guard.ts`) inside `gateFields`; a flagged field drops to low with a fixed question.
- **Changing the prompt, schema, output cap or models makes the recordings in `evals/recordings/` stale**, and `npm run eval` and `tests/unit/injection.test.ts` fail until they are re-recorded with `npm run eval -- --live` (real calls, one run per stale fixture per provider, 0.50 USD cap). Fixture PDFs are generated by `evals/pdf.ts`; regenerate with `npm run eval -- --write-fixtures`.
- Known gaps are in SECURITY.md under "What remains": the old path's forged runs and trusted band until migration 3, per-tenant churn, a large run in flight holding its organization's budget, the secret key's reach, pg_net's grants.

## Auth and tests

- The dashboard sets the **minimum password length to 15**, and the suite proves Supabase enforces it with a direct 14 character `signUp`. Supabase caps passwords at 72 characters. Test passwords are 40 characters. The sign-up form enforces both client-side and shows Supabase's `weak_password` reasons.
- `tests/tenant-isolation.test.ts` signs up **three users once per run** (A, B, D) and reuses them, to stay under Supabase Auth's sign-up rate limit. Tests within the file are order-dependent (B is promoted and later removed; D deletes their own account). Cleanup in `afterAll` removes files, then tenants, then accounts, and fails the run if anything is left. Only PDF blobs are uploaded because of the bucket's MIME list.
- `tests/extraction.test.ts` signs up **two more** (X owns eight tenants, Y is a member of one). It enqueues as X and delivers each run with the local worker runner and fake or replayed providers (`invoice-usd` with its OpenAI recording), checking what the database recorded. It refuses to start if the test project's queue isn't empty, drains any leftover run at no cost in `afterAll`, and asserts the suite spent under 0.01 USD. The ceilings, the sweep and the stale-run reaper can't be reached through the API without permanent spend or backdating, so they are tested by `supabase/tests/extraction_queue.sql` and `extraction_stale_runs.sql` in rolled-back transactions (`npm run test:db`), which also refuse to run while a run is in flight on the test project.
- The Vitest config aliases `@` to `src/`, so tests import the extraction library directly. Modules that import `server-only` (the two providers and `select.ts`) can't be imported by tests; keep secrets behind that line and test the orchestrator with fake providers.
